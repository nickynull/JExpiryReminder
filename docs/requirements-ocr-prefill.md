## 1. 背景与目标

### 1.1 现状

物品录入是全手动流程：用户需要自己输入名称、选分类、翻包装找生产日期、算保质期、填到期日。录入一件物品平均要 30 秒以上，批量录入新购食品时负担明显，这是当前产品最大的使用摩擦点。

物品照片目前只在录入后作为存证使用（每件最多 6 张），本身没有产生任何自动化价值。

### 1.2 目标

拍照或选图后自动预填**物品名称**与**日期信息**，把单件录入时间从 30 秒降到 10 秒以内。

### 1.3 已确认的产品决策

| 决策 | 结论 | 理由 |
|---|---|---|
| 自动化程度 | **预填待确认**，不做全自动入库 | 到期提醒应用里，一个错误的到期日比空白更糟——会导致误提醒或漏提醒，直接损害产品可信度 |
| 精度与体积的取舍 | **精度优先**，可接受 APK 从 7.8MB 涨到 30MB 量级 | 用户明确不设体积上限 |
| 联网 | **永久零联网**，不新增 `INTERNET` 权限 | 现有 manifest 本就无网络权限，这是可验证的隐私承诺，不能为 OCR 破例 |
| 入口位置 | **首页「添加」按钮旁新增「图像识别」按钮** | 识别是「录入的另一种起点」，与添加平级；放在编辑页内会导致用户先填一半再想识别，流程割裂 |
| 采集方式 | **一次最多 6 张照片**，点确定后统一识别 | 品名、日期、配料常分散在包装多个面；6 张与「每件最多 6 张图片」的既有规则一致，识别用的照片可直接作为物品图片，无需二次拍摄 |
| 识别时机 | **选完照片、点「确定」之后才识别** | 选图阶段可自由增删，不做无谓的识别开销；取消选图不产生任何落盘文件 |
| 多图品名冲突 | **列出候选让用户选**，不擅自决定 | 品名错一眼可见，但让用户从 3 个候选里点一下的成本远低于自己重敲；比赌一个最高分更稳 |

### 1.4 成功标准

用户选完照片后，**至少有一项字段被正确预填**，且**没有任何一项被错误填充**。

## 2. 范围

### 2.1 做

- 首页新增「图像识别」入口，进入选图页
- 拍照与相册混合选图，上限 6 张，可逐张删除
- 点「确定」后逐张本地 OCR，多张结果合并
- 带识别结果与全部照片进入添加页，字段预填、日期候选列出
- 品名有多个候选时列出供用户点选
- 6 张照片直接作为物品图片，无需用户再拍一次

### 2.2 不做

| 不做的事 | 原因 |
|---|---|
| 识别无包装物品（水果、散装物、线缆） | OCR 无从下手；离线图像分类只能给出 `bottle`/`box` 级别的粗类，与内置分类体系（食品/药品/化妆品/日用品/自定义）对不上，价值为负 |
| 全自动入库、无需确认 | 与 1.3 决策冲突 |
| 编辑页内对已有图片重新识别 | 本期不做，降为 P2。入口集中在首页，避免同一功能两个入口造成认知负担 |
| 识别配料表、营养成分、价格 | 与产品核心场景无关，且大幅拉高识别失败面 |
| 联网调用云端 OCR | 违背零联网承诺 |
| 手写体识别 | ML Kit 中文对印刷/喷码效果好，手写体不可靠，不做承诺 |
| 图片裁剪、旋转、透视校正 | P2 再评估，本期只用原始照片 |

## 3. 用户场景

### 3.1 主场景（拍照识别新增）

1. 用户在首页点「图像识别」（「添加」按钮旁）
2. 进入选图页，拍下包装正面（品名）
3. 再点「从相册选择」，补上之前拍好的喷码日期照片
4. 选图区显示 2 张，右上角可单独删除某张
5. 点「确定」，进入识别进度页，显示「正在识别 2/2」
6. 识别完成，自动进入添加页：名称、分类、生产日期、有效期已填好，候选区列出检出的日期
7. 用户核对、修改、保存。两张照片已在图片区，无需再拍

### 3.2 简化场景

只拍一张就点确定——流程退化为「拍一张，识别，进添加页」，与直觉一致。

### 3.3 失败场景

- **部分失败**：6 张里只有 2 张读出内容，其余跳过，用读到的部分预填
- **全部失败**：仍进入添加页（照片已带入），只提示「没识别到日期，请手动填写」，表单留空
- **用户不想等**：进度页提供「跳过」，直接带着照片进添加页，不预填
- **取消**：在选图页返回，直接回首页，不产生任何文件

### 3.4 对照：纯手动路径不变

点「添加」还是原来的空白表单，老用户习惯不受影响。识别是新增的第二条路径，不是替换。

## 4. 功能需求

### FR-1 首页入口

- FR-1.1 在现有「添加」FAB 旁新增「图像识别」FAB
- FR-1.2 两者仅在非多选态显示（与现有添加按钮的显示条件一致）
- FR-1.3 视觉主次：添加保持现有品牌黄（`0xFFFFC107`），识别用次要容器色或描边样式，不与主按钮抢视觉重心
- FR-1.4 布局建议：右下角纵向堆叠两个 FAB，识别在上、添加在下，保留现有 `CircleShape`
- FR-1.5 点击后进入选图页；若 OCR 引擎不可用（初始化失败），该按钮不显示，不弹任何报错

### FR-2 选图页

- FR-2.1 独立页面，标题「选择照片」，左上角返回
- FR-2.2 支持两种来源：拍照（`ActivityResultContracts.TakePicture`，临时文件置于 `cache/camera/`）、相册（系统 Photo Picker 多选，一次最多取 `6 - 已选数` 张）
- FR-2.3 总数上限 6 张，达到上限后两个来源按钮禁用并提示「最多 6 张」
- FR-2.4 已选照片以 3 列网格展示，每张右上角有删除按钮，可逐张移除
- FR-2.5 两种来源可任意混合
- FR-2.6 底部「确定（n/6）」，n=0 时禁用
- FR-2.7 **此阶段只持有内存中的 Uri，不落盘**。用户返回或退出，零残留
- FR-2.8 空态引导文案：「拍包装正面 + 日期喷码，识别更准」

### FR-3 识别执行

- FR-3.1 点「确定」后进入识别进度页，逐张处理，显示「正在识别 k/n」与线性进度
- FR-3.2 单张处理顺序：读取 Uri → 压缩（最长边 1280 / JPEG 85，复用 `ImageStore` 现有逻辑）→ `ImageStore.saveCompressedImage` 落盘得到 `ExpiryImage` → OCR → 累积结果 → 释放该张字节数据
- FR-3.3 **串行处理**，不并行。ML Kit 识别器实例不宜并发调用，且串行能让进度真实反映进展
- FR-3.4 进度页提供「跳过」，立即停止后续识别，带着已落盘照片与已得结果进入添加页
- FR-3.5 单张超时上限 5 秒，超时按该张失败处理
- FR-3.6 单张失败（解码失败/OCR 异常）不中断整体，记录后继续下一张
- FR-3.7 全部图片读取失败 → 停留在选图页并提示重选，不进入添加页
- FR-3.8 识别过程中返回 → 中止并回选图页，已落盘的图片需清理，不留孤儿文件

### FR-4 多图结果合并

- FR-4.1 每张图独立产出「名称候选 / 日期候选 / 保质期候选」，再按 §5.7 合并为单一预填结果
- FR-4.2 同一日期值在多张图中重复出现时视为交叉印证，提高置信度
- FR-4.3 合并后仍有多个日期时，全部进候选区，不在预填阶段武断选择

### FR-5 日期抽取

- FR-5.1 识别以下日期书写格式（详见 §5.2）
- FR-5.2 依据邻近关键词区分「生产日期」与「有效期至」
- FR-5.3 识别相对保质期（如「保质期 12 个月」），与生产日期组合推算到期日
- FR-5.4 每个检出的日期附原始文本行，供用户核对
- FR-5.5 过滤批号、净含量、执行标准号、电话等非日期数字

### FR-6 预填规则

添加页按以下优先级填充，**任一场景只填能确定的部分**：

| 识别到的内容 | 生产日期 | 有效期 | 到期日 |
|---|---|---|---|
| 生产日期 + 保质期 | 填入 | 填入 | 由 `ExpiryCalc` 推算 |
| 仅「有效期至」 | 留空 | 留空 | 直接填入 |
| 「有效期至」+ 生产日期 | 填入 | 按差额反推填入 | 直接填入 |
| 仅生产日期 | 填入 | 留空 | 留空 |
| 无 | 全部留空 | | |

> 现有 `ExpiryCalc` 已支持「生产日期 + 有效期 → 到期日」与「只填到期日」两种模式，无需改动推算逻辑。

### FR-7 品名抽取

- FR-7.1 取 OCR 结果中字号最大（boundingBox 高度最大）的文本行作为名称候选
- FR-7.2 排除日期行、保质期行、净含量/配料/地址/电话/条码等行政信息行
- FR-7.3 长度限定 2–20 字，中文字符占比 > 50%
- FR-7.4 抽取不到有效品名时名称留空，不拿「图片 1」之类的占位内容充数
- FR-7.5 多张图各自产出候选后，按 §5.8 聚类、排序、截断，形成品名候选列表
- FR-7.6 候选数 ≥2 时显示候选区，预填最高分并选中；候选数 ≤1 时直接预填，不显示候选区
- FR-7.7 用户点选候选后，名称输入框内容被覆盖，且该字段不再视为「识别未确认」
- FR-7.8 名称输入框始终可直接编辑，候选是快捷方式而不是锁定选项

### FR-8 分类推断（P1）

- FR-8.1 依据品名关键词推断分类：命中「牛奶/酸奶/面包/饮料」→ 食品；「胶囊/片/口服液/颗粒」→ 药品；「面膜/精华/洗发水/防晒」→ 化妆品
- FR-8.2 分类优先级：识别结果 > 首页当前筛选分类 > 默认「食品」
- FR-8.3 推断结果同样标注「识别」徽标，用户可改
- FR-8.4 未命中则回落到现有规则（默认食品，若首页正筛选某分类则预选该分类）

### FR-9 添加页改造

- FR-9.1 `EditScreen` 新增可选参数接收预填草稿：`prefill: PrefillDraft? = null`
- FR-9.2 各字段初值改为 `existing?.x ?: prefill?.x ?: 默认值`，不破坏现有编辑逻辑
- FR-9.3 **预填进入时不自动聚焦名称框、不自动弹键盘**（现有逻辑为 `existing == null` 时聚焦，需追加 `prefill == null` 条件）——字段已有值，弹键盘会遮挡结果
- FR-9.4 预填照片通过 `images` 初值带入，已是落盘后的 `ExpiryImage`，复用现有图片区渲染
- FR-9.5 被机器填充的字段旁显示「识别」徽标，用户在该字段产生手动输入后徽标消失
- FR-9.6 检出 ≥2 个日期时，在日期字段上方显示候选区
- FR-9.7 用户点选某候选，立即覆盖对应字段
- FR-9.8 无预填内容时，添加页行为与现在完全一致

### FR-10 失败与降级

- FR-10.1 未检出任何有效字段 → 进入添加页后 Snackbar 提示，表单保持空白
- FR-10.2 所有识别异常都必须 try-catch 兜底，绝不能让 OCR 异常导致添加页崩溃
- FR-10.3 任何异常路径都不能产生「添加页打不开」的结果

## 5. 规则规格

这是本需求的核心，落地质量取决于此，而非 OCR 引擎。

### 5.1 处理管线

```
选中的 n 张图（n ≤ 6）
  └─ 逐张：压缩落盘 → OCR（返回文本行 + boundingBox）
       ├─ 文本归一化（全半角、去空格、中文数字转阿拉伯数字）
       ├─ 日期抽取（正则 + 关键词邻近）
       ├─ 合理性校验（年份区间、先后关系）
       ├─ 打分
       └─ 品名抽取（版面分析）
  └─ 多图合并（§5.7）
  └─ 分类推断（关键词表，P1）
  └─ 预填模型 → 添加页
```

### 5.2 日期格式

| 格式 | 示例 | 说明 |
|---|---|---|
| `yyyy[-./]MM[-./]dd` | 2026-03-15 | 常规分隔符，最可靠 |
| `yyyy年M月d日` | 2026年3月15日 | 中文格式 |
| `yyyyMMdd` | 20260315 | 8 位连续数字，需关键词邻近才接受 |
| `yyMMdd` | 260315 | 6 位，**仅在紧邻日期关键词时接受**，否则丢弃 |
| `dd/MM/yyyy`、`MM/dd/yyyy` | 15/03/2026 | 日月歧义，两数均 ≤12 时无法判定 |

**歧义处理**：`dd/MM` 与 `MM/dd` 无法区分时，优先取能通过 §5.4 合理性校验的那个；两者都通过则判为不确定，只作候选不预填。

### 5.3 关键词表

| 角色 | 关键词 |
|---|---|
| 生产日期 | 生产日期、生产、制造日期、包装日期、灌装日期、PD、MFD、MFG、PROD |
| 有效期至 | 有效期至、有效期、有效至、保质期至、最佳食用日期、最佳赏味期、此日期前食用最佳、EXP、BBE、BB、USE BY |
| 保质期（相对量） | 保质期、SHELF LIFE，后接 `<数字> 天/日/个月/月/年` |

**匹配窗口**：关键词与日期数值的字符距离 ≤ 12 个字符（同一行优先，允许跨行但降权）。

### 5.4 合理性校验与打分

基础分 **0.55**，按下表加减。选 0.55 而不是 1.0 是刻意的：预填阈值是 0.7，这样**没有关键词锚定的日期永远进不了预填**，只能出现在候选区——包装上同时印着生产日期、批号、有效期，猜错的代价（错误提醒）远大于留空。

| 条件 | 调整 |
|---|---|
| 关键词与数值同行 | +0.3 |
| 年份在 `[当前年-30, 当前年+20]` | 通过；否则直接丢弃 |
| 到期日早于生产日期 | 丢弃 |
| 到期日距今超过 50 年 | 丢弃 |
| 到期日已过去超过 2 年 | −0.4（可能是旧包装或误识） |
| 8 位以上纯数字且无关键词邻近 | 丢弃（多为批号、条码） |
| 同一图片内出现多个相同值 | 各 +0.1（交叉印证） |

**阈值**：≥ 0.7 直接预填；0.4–0.7 列为候选但不预填；< 0.4 丢弃。

### 5.5 与「批号」的区分

批号常与生产日期同格式，是最大的误识别来源。判据：

- 行内出现「批号 / 批 号 / Lot / LOT / 生产批号」→ 该数字判为批号
- 数值虽符合日期格式但年份落在 `[当前年-30, 当前年]` 之外 → 判为批号
- 同一行同时出现两个日期格式数字 → 前者多为生产日期，后者多为有效期

### 5.6 品名抽取

1. 取 boundingBox 高度 Top-3 的文本行
2. 逐行剔除：含 §5.3 关键词、含「净含量/规格/配料/营养成分/生产商/地址/电话/网址/执行标准/SC/条形码」、纯数字、纯符号、长度 < 2 或 > 20、中文占比 ≤ 50%
3. 剩余行中取字号最大者为品名，次之为备选候选
4. 全部被剔除则留空

> 品牌名与品名常分两行（如「特仑苏」/「纯牛奶」）。当前策略只取字号最大的一行，不做拼接——拼接容易产出「伊利安慕希希腊风味酸奶」这类过长且不稳的结果，宁可给短一点的候选让用户补。

### 5.7 多图合并

v0.2 新增流程带来的规则。6 张图大概率是同一物品的不同面（正面品名、侧面配料、底部喷码）。

| 字段 | 合并策略 |
|---|---|
| 名称 | 取所有图中评分最高的候选；若 ≥2 张图给出相同或高度相似（编辑距离 ≤ 2）的文本，该候选 +0.2 |
| 日期 | 跨图汇总为候选池，同值合并并记录出现次数；出现 ≥2 次 +0.15（跨图交叉印证） |
| 保质期 | 取评分最高的候选 |
| 分类 | 基于合并后的最终品名推断，不看单图结果 |

**冲突处理**：不同图给出不相上下的品名（可能拍了两件不同物品）→ 按 §5.8 聚成候选列表，预填最高分并允许用户改选，不擅自锁定。

**上限保护**：候选池最多保留 8 条，超出按分数截断，避免候选区刷屏。

### 5.8 品名候选

#### 生成

1. 收集所有图的品名候选（每图按 §5.6 取 Top-3）
2. 归一化：去空格与标点、全角转半角、去首尾多余字符
3. 聚类：归一化后编辑距离 ≤ 2 视为同一候选，合并时取字符更完整的一条，累计出现图数与最高分
4. 排序：按分数降序，出现 ≥2 张图的候选 +0.2（多图一致属于强信号）
5. 截断：最多保留 4 条

#### 展示条件

| 候选数 | 行为 |
|---|---|
| 0 | 名称留空，无候选区 |
| 1 | 直接预填，无候选区 |
| ≥2 | 预填最高分并选中，显示候选区 |

即：不只在「多图冲突」时展示。单图内版面分析产出多个候选时同样走这个 UI，规则统一，减少分支。

#### 与日期候选的差异

两类字段的容错要求不同，不要统一处理：

- **日期错了会导致误提醒**，用户事后很难发现，所以 0.4–0.7 的结果只作候选不预填，宁可留空
- **品名错了用户一眼可见**（打开列表就看到「这是什么东西？」），所以即使两个候选分数接近，也直接预填最高分，不降级为空白

品名候选的价值不是提升准确率，而是把「必须猜对」降级为「候选里有对的」——指标口径也随之从 Top-1 准确率改为候选覆盖率（§9.1）。

## 7. 非功能需求

### 7.1 隐私与联网

- **不新增 `INTERNET` 权限**，保持 manifest 现状
- OCR 模型随 APK 打包，运行期不发起任何网络请求
- 图片不离开设备，不写入任何临时上传缓存
- 建议在 README 与设置页「关于」中明示「识别全程离线」，作为差异化卖点

### 7.2 体积

release APK 实测 **29MB**（原 7.8MB），debug 33MB。发布说明中需提示用户。

体积主要花在 ML Kit 的 native 库上（`libmlkit_google_ocr_pipeline.so` 每个 ABI 约 7–11MB），模型本身只有 2.5MB。已用 `ndk.abiFilters` 只保留 `arm64-v8a` 与 `armeabi-v7a`，裁掉 x86/x86_64 省了约 23MB——**代价是 x86 模拟器装不上，真机不受影响**。

后续若还要再压：开启 release 的 minify 能砍掉大量未用类（目前 `isMinifyEnabled = false`），但需补 keep 规则并单独验证。

### 7.3 性能

| 指标 | 目标 |
|---|---|
| 单张识别耗时（1280px 长边，中端机） | P50 < 1.0s，P95 < 2.0s |
| 6 张全流程（压缩 + 落盘 + OCR） | P95 < 8s，必须有进度反馈 |
| 首次模型加载 | < 1.5s |
| 峰值内存增量 | < 150MB（逐张处理，单张字节用完即释放） |
| 连续识别 6 张 | 无 OOM、无明显发热 |

### 7.4 兼容性

- minSdk 26 满足 ML Kit 要求，无需调整
- 必须在**无 Google Play 服务**的设备上正常工作（这是选 bundled 版的根本原因）
- 系统 Photo Picker 在 minSdk 26 上会回退到 `ACTION_OPEN_DOCUMENT`，多选能力需实机验证
- 32 位 ABI 设备需实测内存表现

### 7.5 稳定性与文件管理

- OCR 全链路异常隔离，任何异常降级为「识别失败」而非崩溃
- 选图阶段不落盘；点「确定」后才写文件，取消选图零残留
- 识别被中止时，已落盘但未进入添加页的图片需清理，不得留孤儿文件
- 临时拍照文件（`cache/camera/`）在压缩落盘后立即删除，沿用现有做法

## 8. 技术方案

### 8.1 引擎选型

采用 **ML Kit 文字识别 v2 中文 bundled 版**：

```kotlin
implementation("com.google.mlkit:text-recognition-chinese:16.x")
```

**关键约束**：必须使用 `com.google.mlkit:text-recognition-chinese`（模型打包进 APK，真正离线），**不可**使用 `com.google.android.gms:play-services-mlkit-text-recognition-chinese`（依赖 Google Play 服务，首次需联网下载模型，国产 ROM 多数不可用）。

版本号以官方最新稳定版为准，引入时锁定具体版本并写入依赖说明。

### 8.2 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 云端 OCR API | 违背零联网承诺 |
| Tesseract4Android | 中文精度明显弱于 ML Kit，复杂版面易混排，体积优势也不大 |
| PaddleOCR（ncnn/ONNX 移植） | 密集小字精度略优，但需自建 JNI + 前后处理，工程量约为 ML Kit 的 3–5 倍；作为后续精度不足时的备选 |
| 双引擎串联 | 收益边际，却要付出双倍体积与首帧延迟，不做 |
| 6 张图并行 OCR | 识别器实例并发调用不可靠，且进度无法线性反馈，串行更稳 |

### 8.3 新增结构

```
app/src/main/java/com/jimmy/expiryreminder/
├── ui/
│   ├── PickImagesScreen.kt    # 选图页（拍照 + 相册混合，≤6，可删）
│   └── OcrProgressScreen.kt   # 识别进度页（进度 + 跳过）
└── ocr/
    ├── OcrEngine.kt           # ML Kit 封装，单例，预热
    ├── TextNormalizer.kt      # 全半角、空格、中文数字归一
    ├── DateExtractor.kt       # 正则 + 关键词 + 打分
    ├── NameExtractor.kt       # 版面分析取品名
    ├── ResultMerger.kt        # 多图结果合并（§5.7）
    ├── CategoryGuesser.kt     # 关键词表推断分类（P1）
    └── PrefillDraft.kt        # 预填数据模型（内存态，不持久化）
```

### 8.4 页面流转

```
Home ──「图像识别」──> PickImages ──「确定」──> OcrProgress ──完成/跳过──> Edit(prefill)
  └──「添加」──────────────────────────────────────────────────>  Edit(prefill = null)
PickImages / OcrProgress 均可返回上一级并丢弃
```

导航沿用现有 `MainActivity` 的三屏导航方式，新增两个 screen 值。

### 8.5 数据模型

**不修改 `data.json` 格式，维持 v5。**

`PrefillDraft` 只作为页面间传递的内存对象，不持久化，理由：

- 备份兼容性零风险（v5 的 `items`/`categories`/`categoryColors` 结构不动）
- 识别来源信息对用户没有长期价值
- 避免为了 UI 徽标引入一个必须长期维护的字段

预填图片使用落盘后的 `ExpiryImage`，与现有 `Item.images` 结构一致。

### 8.6 测试

- `TextNormalizer`、`DateExtractor`、`NameExtractor`、`ResultMerger` 均为纯函数，写入 JVM 单元测试（现有测试框架已具备真实 `org.json` 依赖，无需新增）
- 目标：日期抽取规则不少于 40 条断言（各格式 × 各关键词 × 各干扰项）；合并规则不少于 10 条（单图、多图一致、多图冲突、跨图印证）；品名聚类不少于 8 条（编辑距离边界、归一化、合并取完整者、4 条截断）
- POC 用的真实照片与标注结果不入库，仅保留统计结论

## 9. 验收指标

### 9.1 功能验收

以 POC 建立的样本集（40–60 张真实包装照）为基准：

| 指标 | 定义 | 门槛 |
|---|---|---|
| 日期检出率 | 有日期的样本中，至少抽出一个日期格式数字的比例 | ≥ 75% |
| 日期解析正确率 | 最终预填的日期与人工标注一致的比例 | ≥ 85% |
| 品名可抽取率 | 有包装样本中抽出有效品名的比例 | ≥ 70% |
| **品名候选覆盖率** | 正确品名出现在候选列表（含自动预填的那条）的比例 | **≥ 90%** |
| **误填率** | 预填了非空值但错误的比例 | **≤ 5%（硬门槛）** |
| 多图合并增益 | 多图输入相对单图的正确率提升 | ≥ 10 个百分点 |
| 单张耗时 | 1280px，中端机 P95 | < 2.0s |
| 6 张全流程耗时 | 含压缩落盘，P95 | < 8.0s |
| 崩溃 | 全流程 | 0 |

**误填率是最高优先级指标。** 宁可什么都不填，也不能填错。

### 9.2 不达标时的处置

- 日期解析正确率 < 70% → 收窄场景至药品、化妆品（包装规范、日期格式统一），或砍掉功能
- 误填率 > 5% → 提高预填阈值（0.7 → 0.85），把更多结果降级为候选
- 品名可抽取率 < 50% → 品名不自动填，只保留日期识别
- 品名候选覆盖率 < 90% → 放宽候选条数上限（4 → 6）或收窄 §5.6 的排除词表
- 6 张耗时超标 → 改为只识别前 3 张

## 12. 风险与开放问题

### 12.1 取景引导的成本

现有拍照走 `ACTION_IMAGE_CAPTURE` Intent（系统相机），**无法在上面叠加取景框，也无法控制对焦与曝光**。而取景引导恰恰是提升识别率最有效的手段（高于更换引擎）。

- 保守方案（P0 采用）：继续用系统相机，仅通过选图页引导文案提示「拍包装正面 + 日期喷码」，成本近零
- 完整方案（P2）：改用 CameraX 自建预览页 + 取景框，需新增 `CAMERA` 权限声明，是本需求中工程量最大的单项

建议先用 POC 数据判断识别率是否够用，再决定是否为取景框付费。

### 12.2 精度提升的性价比排序

若实测精度不足，按下表顺序投入，**不要先去换引擎**：

| 优先级 | 手段 | 预期收益 | 成本 |
|---|---|---|---|
| 1 | 拍摄引导（取景框 / 文案） | 高 | 文案近零，取景框高 |
| 2 | 图像预处理（灰度 + 对比度拉伸，针对反光喷码） | 中高 | 低 |
| 3 | 多帧择优选（连拍 3 帧取最优） | 中 | 中 |
| 4 | boundingBox 版面分析优化 | 中 | 低 |
| 5 | 更换 PaddleOCR 引擎 | 低中 | 高 |

### 12.3 其他风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 点阵喷码 / 曲面反光识别率低 | 核心信息抽不到 | POC 量化；靠 §12.2 手段缓解；承认边界并在文案中引导 |
| 批号被误认为日期 | 直接拉高误填率 | §5.5 规则 + 合理性校验，列入 POC 重点观测 |
| 6 张串行耗时过长 | 用户中途放弃 | 进度反馈 + 跳过按钮；超标则减至 3 张 |
| 选图取消后的文件残留 | 占存储 | 选图阶段不落盘，确定后才写，从流程上避免 |
| Photo Picker 在旧系统回退行为差异 | 多选能力不一致 | minSdk 26 实机验证，必要时回退到自建文件选择 |
| ML Kit 与 AGP 9.1 兼容性 | 构建失败 | 接入时立即验证；AGP 9 内置 Kotlin，注意不要冲突引入 kotlin 插件 |
| release 未开混淆（当前 `isMinifyEnabled = false`） | 未来开启需补 keep 规则 | 在 `proguard-rules.pro` 预留 ML Kit keep 规则 |
| 国产 ROM 无 GMS | 若误用 unbundled 版则功能全废 | §8.1 已写死约束，Code Review 时重点检查依赖坐标 |

### 12.4 待定

- 「图像识别」按钮的图标与文案：`PhotoCamera` + 「识别」是否够清楚，要不要写成「拍照识别」
- 识别功能是否给用户开关（部分用户可能不想要额外的 20MB）—— 需产品决策
- 药品这类「有效期至」与「生产日期 + 有效期」两种印法混用的品类，是否需要单独规则 —— 待样本验证
- 识别入口是否也在首页空列表时做引导位，提高发现率

### 13.2 实现期发现并修掉的问题

这三个都不是设计问题，是动手之后才暴露的：

**1. ML Kit 会把网络权限合并进 manifest。**
引入依赖后，合并产物里多出 `INTERNET` 和 `ACCESS_NETWORK_STATE`。用户安装后会在系统权限列表里看到「网络访问」，直接毁掉「零联网」这个卖点。已在 `AndroidManifest.xml` 用 `tools:node="remove"` 显式移除，并用合并后的 manifest 验证过——只剩通知、闹钟、开机广播、震动四个权限。

**2. native 库让 APK 从 29MB 涨到 56MB。**
`libmlkit_google_ocr_pipeline.so` 每个 ABI 7–11MB，四个 ABI 合计 41MB，而模型才 2.5MB。用 `ndk.abiFilters` 只留 `arm64-v8a` + `armeabi-v7a`，砍掉 x86/x86_64 后省 23MB。**副作用：x86 模拟器装不上**，真机不受影响。

**3. 非法日期会让整次识别崩溃。**
包装上被误识成 `2026-13-45` 时 `LocalDate.of` 直接抛 `DateTimeException`，这个异常会一路冒到 UI。单测抓到了它，已在 `parseMatch` 里兜住。这类问题如果上线后再发现，表现就是「拍了张照片 App 崩了」，且极难复现。

### 13.3 与文档的偏差

| 项 | 文档原定 | 实现 | 原因 |
|---|---|---|---|
| 日期打分基础分 | 1.0 | **0.55** | 1.0 会让无关键词的日期也达到预填阈值，与「无锚定不预填」的原则矛盾 |
| 进度页返回 | 中止并回选图页 | 回选图页且**带回已选照片** | 直接丢弃会让用户白拍一遍 |
| 拍照缓存清理 | 压缩落盘后立即删除 | 保留，由系统回收 cache | 从进度页返回选图页还要用它做缩略图 |
